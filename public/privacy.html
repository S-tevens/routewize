1. Scope and who this applies to

This Privacy Policy explains how [Legal Entity Name, e.g. "Routewize Inc." or the founders' registered business name] ("routewize," "we," "us," or "our") collects, uses, stores, and discloses information in connection with the routewize service: an API proxy that sits between a customer's application and their OpenAI and/or Anthropic accounts, providing semantic response caching and cost-based model routing (the "Service").

This policy covers two distinct groups, and treats them differently:

  • Customers — the businesses or individuals who sign up for routewize, receive a routewize API key, and configure the Service. Customers provide their own OpenAI/Anthropic provider keys to us.
  • End Users — the people who interact with a Customer's own application, which happens to route its LLM calls through routewize. routewize has no direct relationship with End Users and does not know their identities. Data protection obligations toward End Users are primarily the Customer's responsibility as the operator of their own application; this policy describes what routewize itself does with the request data that passes through it on a Customer's behalf.

This policy does not cover third-party websites, the OpenAI or Anthropic platforms themselves, or any other service linked from routewize's website — each has its own privacy policy.

3. Information we collect

3.1 Account and contact information

When a Customer signs up, we collect what is reasonably necessary to operate an account: name, email address, company or product name, and any billing information required once paid plans are introduced. [Update this section once a real signup/billing flow exists — as of this draft, customer onboarding is manual and this data is held directly by the operator, not through an automated signup system.]

3.2 Provider API keys

To make calls to OpenAI and/or Anthropic on a Customer's behalf, the Service requires the Customer's own Provider Keys. These are stored server-side, associated only with that Customer's account, and are used exclusively to serve that Customer's own requests. Provider Keys are never shared across Customers, never resold, and never used to make calls unrelated to that Customer's own configured traffic.

As an interim security measure, Provider Keys referenced in the Service's configuration are resolved from environment variables at server startup/reload rather than being committed to disk in plaintext configuration files. A dedicated secrets-management system (e.g. a cloud provider's secrets manager or HashiCorp Vault) is planned as the Service scales beyond its current early stage — see §9.

3.3 Request metadata (persistently logged)

Every request that passes through the Service generates one log record containing only the following fields — never the content of the request or response (see §4):

  • A one-way cryptographic hash of the Customer's API key (used to attribute the record to a Customer without storing the key itself in the log)
  • The model requested by the Customer's application, and the model actually used to serve it
  • Whether the request was served from cache (a "cache hit") or required a real call to a Provider
  • Which routing rule, if any, matched and determined the model used
  • Token counts and computed cost/savings figures (broken down by cache savings, routing savings, and provider-native prompt-caching savings where applicable)
  • A timestamp

This metadata is what powers the Customer-facing dashboard (usage stats, savings reporting) and, in aggregate, an internal administrative view used to monitor the health and scale of the Service across all Customers (see §12).

3.4 Prompt and response content — transient, cache-only, not logged

To detect near-duplicate requests, the Service computes a semantic embedding (a numeric representation) of each request and briefly holds the request's text content and the generated response in server memory, scoped strictly to that one Customer, so that a sufficiently similar future request can be served instantly from that memory instead of triggering a new, billable call to a Provider. This in-memory cache:

  • Is never written to disk or to the persistent request log described in §3.3
  • Automatically expires after a configurable time window (24 hours by default, per Customer)
  • Is bounded in size and evicts its oldest entries once a limit is reached
  • Is cleared entirely whenever the Service process restarts
  • Is isolated per Customer — one Customer's cached content is never visible to, or matched against, another Customer's requests

Separately, when semantic caching is enabled, request text is sent to an embedding model to generate the numeric representation used for similarity matching (see §7 for which provider performs this). This applies regardless of which Provider is configured to serve the actual completion — for example, a request destined for Anthropic may still have its text sent to OpenAI's embeddings API for this purpose, unless the Service is configured to use a local, non-API embedding method instead.

3.5 Website and dashboard usage data

The Customer-facing dashboard and the internal administrative view are static pages that run in the Customer's or operator's own browser. A Customer's routewize API key, once entered into the dashboard, is stored in that browser's local storage so it does not need to be re-entered on every visit; it is never transmitted anywhere other than to the Service's own backend, and never to a third party. We do not currently use tracking cookies, third-party analytics, or advertising identifiers on any routewize property. [Update if analytics/cookies are added later.]

4. Information we do not collect

To be explicit about the boundary described above: the Service's persistent, durable logs (the ones retained beyond the transient in-memory cache window, used for billing, dashboards, and administrative reporting) never contain:

  • The text of a Customer's or End User's prompts
  • The text of any model-generated response
  • Any reference documents or context a Customer submits alongside a request

Nothing in the request-logging code path writes this content to disk at any point. The only place prompt/response content exists at all is the transient, in-memory, auto-expiring cache described in §3.4.

5. How we use information

  • To provide the Service — routing requests, serving cache hits, computing costs and savings.
  • To operate Customer accounts — authentication, configuration, rate limiting, and spend caps that a Customer sets for their own account.
  • To generate savings and usage reporting — the dashboard and financial overview a Customer sees are computed entirely from Request Metadata (§3.3); no prompt/response content is ever part of this reporting.
  • To operate and improve the Service — aggregate, cross-Customer metrics (total requests, total spend under management) support internal capacity planning and product decisions. This uses Request Metadata only, never content.
  • To communicate with Customers — service notices, security notices, and (where a Customer has agreed) product updates.
  • To comply with legal obligations and enforce our terms of service.

We do not use Customer or End User prompt/response content to train any machine learning model, our own or otherwise — we do not retain such content long enough to do so, and have no mechanism that would extract it from the transient cache for that purpose.

  • Request Metadata (persistent log): retained indefinitely at present to support historical dashboard reporting. 9. Data security

We apply the following measures today, described accurately rather than aspirationally:

  • Provider Keys are resolved from environment variables at runtime rather than stored in plaintext configuration files committed to source control.
  • Each Customer's data (cache entries, request logs, rate limits) is logically isolated by their unique API key; one Customer's requests cannot access another's cached content or configuration.
  • The administrative, cross-Customer view of the Service is protected by a separate credential from any Customer's own API key, uses no shared authentication code with Customer-facing routes, and is not linked from anywhere a Customer would encounter it.
  • All traffic to the Service should be served over HTTPS/TLS in any production deployment. [Confirm and state the actual deployment's transport security once hosted.]

What we do not yet have, stated plainly because a professional-grade policy should not overclaim: a dedicated secrets-management system (planned — see §3.2), encryption at rest for the request log, formal intrusion detection/alerting, or a completed third-party security audit. [Update this section as each of these is built — see the project's internal production-readiness checklist.] No security measure is perfect, and we cannot guarantee absolute security of any information transmitted to the Service.

12. Internal access controls

A small internal, password-protected view lets the operators of the Service see aggregate figures across all Customers (total requests, spend, savings) for operational purposes — capacity planning, spotting errors, and understanding overall usage of the Service. This view:

  • Uses a separate credential from any Customer's API key, and cannot be accessed with one
  • Displays only the same Request Metadata described in §3.3 — never prompt or response content, because none is ever logged for it to display
  • Is not linked from, or reachable through, any Customer-facing page
