## Before you write any code

1. `git fetch origin && git checkout master && git pull origin master` — work from current `master`, not a stale checkout.
2. Read the **Danger zone** section below before touching any file listed there.
3. Create a new branch off up-to-date master: `git checkout -b feature/<short-description>`. Never commit directly to `master`.
4. Run `npm test` before you start (confirm you're starting from a green baseline) and again before you push.
5. Push your branch and open a PR (`gh pr create` or via GitHub). Don't merge into `master` yourself — leave that for review.
6. **If your change alters the *behavior* of an existing shared mechanism** (not just adds something new), say so explicitly and prominently in the PR description: what the old behavior was, what it is now, and why. A PR titled "add dashboard feature" that also silently changes how caching works is exactly what caused the one real incident in this repo's history so far (see `git log --oneline` around the `codex/token-savings-dashboard` integration, and PR #1's description for the full story) — a one-line callout in review would have caught it immediately.

## Danger zone — flag any behavior change to these explicitly

These are shared, core mechanisms that other work depends on. Adding to them is fine; **silently changing how they already behave is the one thing that has caused real problems in this project.**

- `src/server.js` — specifically the cache-namespace construction and the `/v1/chat/completions` request flow
- `src/cache/semanticCache.js` — the semantic similarity matching itself. If you touch this, verify with a real test that near-duplicate prompts (not just exact-string duplicates) still produce cache hits — that property was accidentally destroyed once already.
- `src/router/rules.js` — routing must stay pure, deterministic, and driven only by customer-configured rules, never by any form of automatic "quality" judgment (this is a deliberate product decision, not an oversight — see CONTEXT.md).
- `scripts/dryRun.js` — this must stay behaviorally identical to the live server's cache+router logic. It's the sales-proof mechanism; if it diverges from what the live proxy actually does, every number it produces becomes a lie to a prospective customer.
- **Streaming (`handleStreamingCall` in `server.js`, `streamOpenAI`/`streamAnthropic`)** has no live end-to-end test in this environment (no real API key) — offline HTTP integration tests cover success/failure paths for both real SDK adapters; real provider success is still unverified. If you have a real key, do one live streaming smoke test before trusting the successful-multi-chunk path, and update GAMEPLAN.md's row for it.

## Known security limitation — documented, not yet mitigated

**Embedding-collision attack on the semantic cache** ("From Similarity to Vulnerability: Key Collision Attack on LLM Semantic Caching," arXiv:2601.23088, verified 2026-09-23). Finding: embedding-based semantic caches are provably vulnerable to adversarial-input collisions — crafted text that looks unrelated to a human but collides in embedding space, forcing a false cache hit (the paper's benchmark: 86% hijack rate).

**Why this is real but low-severity for us right now:** `SemanticCache` is already strictly namespaced per customer (`entriesByCustomer` keyed by `customerApiKey` in `src/cache/semanticCache.js`) — a collision cannot cross customers. Worst case today: one customer's own adversarial end-user input tricks that same customer's own cache into serving a wrong (but still their own) cached answer — an integrity risk for that one customer's traffic, not a cross-tenant data leak.

Not scheduled for a fix — revisit if a real customer's traffic pattern makes this a plausible attack surface (e.g. end-user-supplied, untrusted prompts at volume), not before.

Every item from the original "next things to add" roadmap is now done or explicitly deferred (see the "later" rows below) — the roadmap continues past this point per SYSTEM_DESIGN.md §9 and the Production-readiness checklist below as new gaps surface.

**Async near-miss cache verification (PR #11, merged):** default-off, paid asynchronous cache verification after successful JSON/SSE responses, with strict verdicts, namespace/TTL-safe promotion, and logged judge overhead. Inspired by the "Krites" paper (arXiv:2602.13165). Reviewed before merge (danger-zone files: `src/server.js`, `src/cache/semanticCache.js`, `scripts/dryRun.js`) — existing hit/miss matching confirmed unchanged; the dry run correctly rejects verification-enabled configs instead of silently omitting judge spend; the async trigger correctly uses `res.once("finish")` so an aborted/disconnected response never starts a paid judge call. No real-provider smoke test or measured savings claim yet — opt-in and off by default, so this doesn't block anything.

**The actual bottleneck is not engineering** — it's that there is still no real customer traffic data. Every savings number produced so far is synthetic. Don't let engineering work substitute for getting that data; see CONTEXT.md's "Next steps" for the non-engineering sequence.

## Production-readiness checklist

Everything needed to go from "one unpaid pilot" to "production-grade, multiple real paying customers." In priority order — top items unblock the ones below them more than the reverse. Checked = actually shipped and verified in this repo, not just started. See [SYSTEM_DESIGN.md](SYSTEM_DESIGN.md) §9 for the systems-level "why" behind the infra items, and [NON_TECHNICAL.md](NON_TECHNICAL.md) for the business-side items.

### Core infrastructure
- [x] CI pipeline (`npm test` on every PR)
- [x] Config hot-reload (no restart to change a customer's settings)
- [x] Secrets out of plaintext — env-var substitution (interim; see "later" row for the real fix)
- [x] Per-customer rate limits / daily spend caps
- [x] Streaming support (test-coverage caveat — no live provider run yet)
- [x] Provider-native prompt caching (Anthropic)
- [x] Queryable request log (SQLite index, no full-file scans)
- [x] Async near-miss cache verification (PR #11, merged) — default off, post-response only, paid/logged, reviewed pre-merge; no real-provider verification yet
- [ ] Live streaming smoke test — blocked on a real provider key (see task queue)
- [ ] Persistent, shared cache (Redis + pgvector/Qdrant) — deliberately deferred until there's >1 customer or >1 server process
- [ ] Real secrets manager (Vault/AWS/GCP) — deliberately deferred until there's customer volume to justify it
- [ ] Real config store (database or admin API) instead of one hand-edited YAML file
- [ ] Observability: metrics (request rate/latency/error rate), alerting on provider outages or config errors, log shipping beyond a flat local JSONL file, a correlation ID per request

- [x] Cross-customer admin view — `/admin` + `/admin/api/overview`, gated by a separate `ADMIN_TOKEN` (never a customer's `api_key`), served from its own `admin/` directory sharing no static mount, route, or auth code with the customer surface. See README's "Admin overview" section and `SYSTEM_DESIGN.md` §4.

### Accurate, trustworthy savings (customer-facing — a wrong number here is worse than no number)
- [x] Real provider usage as the source of truth — `priceResponse()` fails closed on missing/unknown pricing rather than guessing (never silently treats a gap as $0 or as savings)
- [x] Baseline-vs-actual shown side by side in the dashboard, not just a single savings delta — new "Live traffic: baseline vs actual" chart on the dashboard, backed by real per-request `cost_estimate` logged in `src/server.js` and aggregated daily in `financialOverview.js` (`live_comparison_daily`). Explicitly a placeholder until real traffic exists: it renders an honest empty state ("No live gateway traffic yet") rather than fabricated data, and will populate automatically the moment a pilot's requests start flowing — nothing to configure. Not yet visually verified in a browser (no local provider keys in this environment); logic is unit-tested.
- [x] Break cache savings, routing savings, and prompt-caching savings out separately — every logged request now carries `savings_breakdown: {cache_usd, routing_usd, prompt_cache_usd}` (`src/server.js`), summed per-period into `cost_saved_breakdown_usd` (`src/logging/financialOverview.js`) and shown under the dashboard's "Cost saved" card. `prompt_cache_usd` is `null` (never `0`) when `cache_write_input`/`cached_input` rates aren't configured — unknown is never shown as zero. Requests logged before this change are excluded from the breakdown (not counted as zero) via `breakdown_priced_requests`. Blended `cost_saved_estimate_usd` is unchanged for backward compat.
- [ ] Reconcile routewize's logged spend against a real customer's actual provider invoice for the same period — do this by hand for the first pilot before ever quoting a savings number to a second customer
